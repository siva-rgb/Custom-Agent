# Product specification — custom-agent-sdk (Phase 0 to Phase 2, increment 1)

> Status: draft. A coding agent must not implement product code until this specification is approved through Genesis.

**Scope:** Stage 1, Phase 0 — the single-agent skeleton — plus the store-hardening requirements (FR-17..FR-21, NFR-8, AC-11..AC-15) that Phase 2 makes reachable, and the distribution and example requirements (FR-22..FR-25, NFR-9..NFR-10, AC-16..AC-19) for publishing the SDK as a standalone project, and, added by the owner's 2026-09-12 roadmap review to land before Phase 2, the honest-results requirements (FR-26..FR-34, NFR-11..NFR-12, AC-20..AC-26) and the safe built-in tools requirements (FR-35..FR-42, NFR-13..NFR-14, AC-27..AC-33). Those were added after Phase 0 was approved, measured rather than assumed: see the Phase 2 readiness section. Phase 2 is specified in two increments (DECISION-ce3b0e78): this document carries the first, M11 to M15 (FR-43 to FR-63, NFR-15 to NFR-20, AC-34 to AC-50), and the orchestrator, budgets, `ContextPolicy`, context compaction and replanning follow in the second. Phases 3–8 each get their own Genesis specification when they start, per the design docs' refusal to write low-level design for components that do not exist yet. Source of truth: `agent_sdk/agent-sdk-low-level-design (1).md` (Phase 0 detail) and `agent_sdk/agent-sdk-master-design-v0.3.md` (design of record).

## Problem

Building multi-agent products on a vendor agent SDK couples every product to one provider's harness, and leaves orchestration state, tool authorization, and evidence provenance as opaque vendor internals. This project builds the harness in-house so those three things are inspectable, portable, and governable.

Phase 0 does not solve that problem. Phase 0 proves the foundation the solution stands on: one agent, one loop, one tool call, fully persisted, fully provenance-tagged, fully tenant-scoped — with the interface seams that Phases 2–8 need already cut, so later phases add implementations rather than replace contracts.

## Users

- **Primary:** the developer building Stage 2's three products (Research Analyst, Software Tester, Agentic RAG) against this SDK's public API.
- **Affected:** operators debugging a run after the fact from persisted state and events; reviewers who must answer "exactly what configuration produced this run" without re-running it.
- **Not a user in Phase 0:** any end user of a Stage 2 product. Phase 0 ships no product.

## Functional requirements

- FR-1: `Runner.run(spec, task, config)` drives one agent to a terminal status of `completed`, `failed`, or `max_turns_exceeded`, and returns a `RunResult` carrying status, output, events, and usage. (Amended for M12: a run can also end `cancelled`, FR-50.)
- FR-2: Canonical primitives `Message`, `Role`, `ToolCall`, `ToolResult` exist provider-independently, and every `ToolResult` carries exactly one `ContentProvenance` (origin, instruction_authority, trust_zone, taint_flags, source_uri_or_hash).
- FR-3: A `ModelClient` protocol with `send(ModelRequest) -> ModelResponse`, implemented by an OpenAI-compatible adapter that calls the configured `BASE_URL` endpoint and maps its response to `ModelResponse` (message, tool_calls, stop_reason, usage, provider_response_id, provider_metadata).
- FR-4: `ToolSpec` (name, description, input_schema, risk_class, read_only, idempotent, approval_policy) and a `ToolRegistry` supporting registration and lookup; duplicate registration raises at registration time, not at call time.
- FR-5: `ToolExecutor` implements the fixed lifecycle — resolve, validate arguments, permission check, approval (auto-allow stub), `before_tool` hook, execute, assign provenance, `after_tool` hook, emit `ToolCalled` — returning a `ToolExecutionOutcome`.
- FR-6: A `PermissionChecker` protocol taking `(tool_call, principal_context)`, with `AllowlistPermissionChecker` as the default implementation.
- FR-7: A minimal `ContextAssembler` builds `ModelRequest` from message history and tool schemas, carrying provenance as request metadata rather than as model-readable instruction text.
- FR-8: A `RuntimeHook` interface with `before_model`, `after_model`, `before_tool`, `after_tool`, wired into `AgentLoop` and `ToolExecutor`, defaulting to `continue` at every point.
- FR-9: A `SessionStore` protocol with Postgres implementation exposing `append(run_id, message)` and `history(run_id)`; `sequence_no` is assigned inside the same transaction as the insert.
- FR-10: `RunEvent` records are emitted and persisted with the full envelope (event_id, schema_version, sequence_no, event_type, tenant/project/run ids, nullable agent/task/tool_call/attempt ids, parent_event_id, correlation_id, timestamp, payload) for the Phase 0 event set: `RunStarted`, `ModelCalled`, `ToolCalled`, `RunCompleted`, `RunFailed`. (Amended for M12: `RunCancelled`, FR-52.)
- FR-11: Exactly one `ExecutionManifest` row is written per run at start, capturing sdk_version, agent_spec hash, instructions_hash, model id/version/adapter_version, tool_spec_hashes, and policy_version.
- FR-12: A `ModelRegistry` records provider, model_id, model_version, adapter_version, and capabilities (max_context_tokens, supports_parallel_tool_calls, pricing). (Amended for M9 with the owner's approval, decision D3: the single `cost_per_token`, which nothing read, is replaced by `ModelPricing`; see FR-30.)
- FR-13: The error taxonomy exists as a hierarchy: `AgentSDKError` → `ModelError` (Timeout, RateLimited, ProviderUnavailable, InvalidStructuredOutput) / `ToolError` (NotFound, ValidationError, PermissionDenied, ApprovalRequired, Timeout, ExecutionError) / `WorkflowError` (BudgetExceeded, MaxTurnsExceeded, MaxDepthExceeded, DependencyFailed, ReplanLimitExceeded, Cancelled).
- FR-14: `AgentLoop` terminates at `max_turns` with status `max_turns_exceeded` as a defined terminal state, never as an exception escaping to application code.
- FR-15: `ModelError.Timeout` and `ModelError.RateLimited` retry up to 2 times with exponential backoff; every other `ModelError` propagates immediately without retry.
- FR-16: Future-seam types are defined but only minimally implemented: `ToolExecutionOutcome` (only `Completed` and `Failed` reachable), `RunInterruption` (type only, no persistence), `ModelRequest.output_schema` (always `None`), `PrincipalContext` (persisted, never read).

### Phase 2 readiness — store hardening

Phase 2 introduces parallel subagents, which makes three Phase 0 assumptions
reachable that Phase 0 could legitimately assume away. Each requirement below
was written against a measured failure, not a suspected one; the measurements
are recorded in `.genesis/project.json` (KNOWLEDGE-e52fb4dc, KNOWLEDGE-010d12d3).

- FR-17: The schema has a versioned migration path. Applying migrations to a database created by an earlier schema brings it to the current version, records which migrations ran, and is idempotent. `apply_schema`'s `CREATE TABLE IF NOT EXISTS` is a no-op for anything new on an existing database, so today a column added to `schema.sql` is silently not created and the code fails later at insert time. FR-17 is ordered first because FR-18 and FR-21 both need a schema change to reach an existing database.
- FR-18: `run_events.sequence_no` is assigned inside the insert from the stored maximum for that run, as `messages.sequence_no` already is — never from an in-process counter. A second event sink for one run (a subagent, or any resumed run) must continue the sequence rather than restart it.
- FR-19: Concurrent appends to one run are available, not merely safe. A losing writer to `messages` or `run_events` retries and commits; no caller ever receives a raw driver exception for a write that a retry would have completed.
- FR-20: Persistence does not block the event loop. Store calls issued from async code use non-blocking I/O and a connection pool, replacing the per-call connect/authenticate/close cycle.
- FR-21: A run may record the run that spawned it, so a subagent's trace reconstructs together with its parent's. `runs` has no such column today.

### Distribution and examples (M8)

M8 publishes the SDK as a standalone project. It adds no SDK capability: every
example uses only what Phase 0 and M7 built, and says so where a reader would
reasonably expect more.

- FR-22: The SDK is installable as a package from a `pyproject.toml` that declares the same runtime dependencies as `requirements.txt`, puts test and example dependencies in optional extras, and ships `schema.sql` and every file in `migrations/` as package data, so `apply_schema` works from an installed copy and not only from a checkout.
- FR-23: A `scripts/` directory holds runnable examples, one activity per file, written against the public API: a minimal agent; custom tools (schemas, validation failures, async tools, timeouts, tool errors); permissions and runtime hooks; persistence and trace reconstruction; switching models; bridging tools from an MCP server; recording a delegated child run under its parent (FR-21); and testing an agent offline with a scripted model client.
- FR-24: Every example runs in two modes: live against the configured gateway (and the database, where the example is about persistence), and offline with `--offline`, using a scripted `ModelClient`, no network and no database, so an example can be checked without credentials.
- FR-25: The MCP example states plainly that the SDK has no native MCP support (Phase 4), bridges an MCP server's tools into `Tool` objects itself, and relabels their results with MCP-origin, untrusted `ContentProvenance` through a `RuntimeHook` -- because the executor records every tool result as a trusted internal tool, which is wrong for content from an external server (ADR-26).

### Honest results (M9)

M9 makes a run's result tell the truth about how it ended and what it cost. Gateway
behaviour quoted below was measured on 2026-09-12 against `openai.gpt-4o-mini` and
`bedrock.anthropic.claude-haiku-4-5`, not assumed. Decisions D1 to D10 are the owner's
of the same date.

- FR-26: A model response whose `stop_reason`, as the `after_model` hook leaves it, is `MAX_TOKENS` or `CONTENT_FILTER` ends the run `failed` with error `max_tokens` or `content_filter` respectively, on whichever turn it arrives, the last turn `max_turns` allows included. The response message is still appended to history and its `ModelCalled` event still emitted, so the record shows what the model produced; but no tool call in that response reaches the executor: no permission check, no `before_tool` hook, no `ToolCalled` event, no tool-result message. A cut-off call list or cut-off arguments cannot be told apart from complete ones, and arguments that decode prove nothing: at the limit, `gpt-4o-mini` returned a tool call with undecodable arguments and Claude Haiku one whose arguments decoded. A filtered response is likewise not the answer the model would have given (D1). `RunResult.output` carries the response text, or None when it had none. An unrecognised stop reason (`OTHER`) ends the run as it does today. `runs.status` already allows `failed`, so no status migration is needed.
- FR-27: Max output tokens can be set on `AgentSpec` and on `RunConfig` as `max_output_tokens`; a run value overrides the agent's. When either is set, every model request of the run carries it, overriding the client's own default. When neither is set, the client's default applies unchanged (1024 for `OpenAICompatibleModelClient`). Invalid values are refused at construction, by field name, like `max_turns`: a bool, a non-int, less than 1, or more than 2**31-1.
- FR-28: A provider-neutral `ReasoningEffort` (`low`, `medium`, `high`) can be set on `AgentSpec` and on `RunConfig`; a run value overrides the agent's. It reaches the provider payload only when set: an unset effort adds no key, so models that reject the parameter are unaffected. Setting a reasoning effort with no explicit `max_output_tokens` on the agent or the run is a configuration error raised at the `Runner.run` call site (D2): with the adapter's 1024 default, Claude Haiku answered HTTP 400 because `max_tokens` must exceed the thinking budget.
- FR-29: `Usage` adds `cache_read_tokens`, `cache_write_tokens` and `reasoning_tokens`, each defaulting to 0 and coerced by `Usage` itself like the existing fields (INVARIANT-3c123c38). Their meaning is fixed and provider-neutral: `prompt_tokens` includes cache-read and cache-write tokens, and `completion_tokens` includes reasoning tokens. That is the gateway's own accounting (2560 cached of 2620 prompt tokens; 25 reasoning of 45 completion tokens). The OpenAI-compatible adapter reads both shapes the gateway returns: OpenAI's `prompt_tokens_details.cached_tokens` and `completion_tokens_details.reasoning_tokens`, and Anthropic's top-level `cache_read_input_tokens` and `cache_creation_input_tokens` beside `prompt_tokens_details.cache_write_tokens`. A quantity reported in two places is counted once. `ModelCalled` carries all six counts, and usage rebuilt from events on the failure path rebuilds all six.
- FR-30: `ModelCapabilities.cost_per_token` is replaced by `ModelPricing`: USD-per-token prices for input, output, cache read and cache write (D3; FR-12 amended). One model call costs `(prompt - cache_read - cache_write) x input + cache_read x cache_read_price + cache_write x cache_write_price + completion x output`, with reasoning billed inside completion and never added again. A call's cost is None when its model has no registry entry or no pricing, or when any token class with a non-zero count has no price. A run's `RunResult.cost_usd` is the sum of its calls' costs, and None if any call's is None: never 0 for an unknown cost, never a partial sum. Money is a `Decimal`, never a float. The model priced is the one the request was sent with. The default registry ships no prices: the gateway's `/model/info` returns 403, and a bundled price that goes stale reports a wrong number rather than an unknown one. Each `ModelCalled` event carries its call's cost, so a failed run's cost reconstructs the way its usage does.
- FR-31: Migration `0003` persists what FR-26 to FR-30 compute (D4). `runs` gains the six token totals and `cost_usd NUMERIC` (NULL when unknown), written wherever a terminal status is written, including the Runner's failure path. `execution_manifests` gains `max_output_tokens`, `reasoning_effort` and the `ModelPricing` used, each NULL when unset, so a cost stays auditable after prices change. Rows written before `0003` keep NULL. `agent_spec_hash` is unchanged, so manifests stay comparable across the migration.
- FR-32: When no model is named, the Runner records the client's default model id (KNOWLEDGE-862c2e9e) in `runs.model_id`, the manifest and the `RunStarted` payload, and prices by it. The id comes from an optional read-only `default_model_id` on the client. `ModelClient` stays `send()`-only: a client without that attribute still works, recording NULL and `unspecified` as today, with a None cost. `OpenAICompatibleModelClient` provides it.
- FR-33: The two M3 limitations in ASSUMPTION-75110765 are closed. (1) The body of an error response cannot change its classification: every 429 is `ModelRateLimited` and retried, and every 5xx is `ModelProviderUnavailable`, whatever the body contains. (2) Redaction is symmetric: no string anywhere in a `ModelResponse` built from a 2xx body contains the credential. That covers content, tool call ids, names, argument keys and values, `provider_response_id` and `provider_metadata`, and holds even where the wire body JSON-escaped the key. A base64, URL-encoded or line-wrapped rendering stays out of reach, as today.
- FR-34: `scripts/09_limits_and_cost.py` shows a run cut off by `max_output_tokens` ending `failed` with `max_tokens`, and a run reporting `cost_usd` from caller-supplied prices, in both FR-24 modes. The README and `scripts/README.md` list it (D9).

### Safe built-in tools (M10)

M10 adds Tier 1 read-only tools a caller must opt into. Every refusal below is an ordinary
tool error the model sees, never a raise and never a run failure.

- FR-35: The module `agentsdk.builtin_tools` provides factories that return `Tool` objects. Importing `agentsdk` does not import it, and nothing registers a built-in tool automatically: a Runner holds only the tools its caller passed. An empty `tool_profile` still denies every built-in call. Every built-in is `RiskClass.READ_ONLY` with `read_only=True`.
- FR-36: The file tools (read, list, glob, grep) are built with a root folder the caller supplies, which must exist and be a directory; it is resolved once, at construction. Every path a file tool reads, lists, matches or returns must resolve, after following every symlink, junction and reparse point, to a location inside the root. That check is made on the file actually opened, not only on the path before opening, so a link swapped between check and open cannot escape. Anything else is refused, without revealing the resolved outside path or its content. Refusal covers every escape form: `..` segments; absolute, drive-letter and drive-relative (`C:x`) paths; UNC and device paths (`\\server\share`, `\\?\`, `\\.\`); reserved device names (`CON`, `NUL`, `COM1`), with or without an extension; alternate data streams (`name:stream`, `::$DATA`); trailing dots and spaces; 8.3 short names; and glob patterns or traversals that would follow a link out. A file with more than one hard link is refused, because a hard link to an outside file cannot be told apart by its path (D6). The root folder is covered by each file tool's schema hash.
- FR-37: The file tools are bounded: a read is capped in bytes; list and glob results are capped in count; grep is capped in matches and skips files larger than the read cap; a binary file is reported, never returned as text. grep matches literal text, not regular expressions (D6): a model-supplied pattern can backtrack catastrophically, and a timeout cannot interrupt a synchronous function. No file tool performs I/O on the event loop's thread.
- FR-38: The HTTP fetch tool is built with a required allowlist, and an empty allowlist refuses every URL. Entries are host names, compared after lowercasing, trailing-dot removal and IDNA normalisation; an explicit `*.` entry admits subdomains. Only http and https are allowed, and a URL carrying userinfo is refused. Every hop is checked, the first request and each redirect up to a redirect cap: the host must match the allowlist, and every address it resolves to must be globally routable. That refuses private, loopback, link-local (including 169.254.169.254), unique-local, unspecified, multicast, shared, reserved, and IPv4-mapped or otherwise embedded forms of those, whether named or written as a numeric host in any spelling. The connection goes to an address that was checked, never to a second DNS answer. Environment proxy settings are ignored: httpx honours `HTTP_PROXY` by default, and a proxy bypasses the address check. Fetch sends no `Authorization`, `Cookie` or `Proxy-Authorization` header, no SDK credential value, and no cookie between hops. The body is read as a stream and stopped at a cap on decoded bytes, so a compressed body is bounded too, and one total deadline covers every hop and the body. A non-text content type is refused. The result records the final URL as `source_uri_or_hash`, and the allowlist is covered by the tool's schema hash.
- FR-39: The web search tool is built with a required `SearchBackend`, a protocol with an async `search(query, max_results)` returning results with a title, URL and snippet. No backend or vendor ships with the SDK. The number of results and the size of each are capped, and a backend exception becomes a tool error.
- FR-40: A `ToolSpec` may declare the provenance of its results: origin, trust zone, instruction authority and taint flags. The default is today's `internal_tool`, so existing tools are unchanged, and executor step 7 applies the declaration. Fetch and search declare `external_tool`, `untrusted`, `data_only`, and the taint flags `external_content` and `prompt_injection_risk`. When the tool ran and then failed (it raised, timed out, or returned unstorable content), the error result carries the declared trust zone, authority and taint, because the error text can carry external bytes (M8 review caveat 3); its source stays the executor's error URN. Failures before the tool ran (not found, validation, permission, `before_tool` rejection) keep `executor_error`; today the `before_tool` rejection passes `tool_reached=True`, and nothing reads that flag yet. Declared provenance and the output cap (FR-41) are covered by `schema_hash`, and a tool that declares neither keeps its current hash.
- FR-41: Every tool, not only built-ins, has an output cap: `ToolSpec.max_output_chars`, a positive int defaulting to 50,000, with no uncapped setting (D5). It applies to every `ToolResult` the executor returns: a success, any error, and content an `after_tool` hook substituted. Content over the cap is cut to the cap, never inside a character, and followed by a marker the model can read that states the original and the kept length. The `ToolCalled` payload records the original length and whether the content was truncated.
- FR-42: `scripts/10_builtin_tools.py` shows file tools confined to a temporary root and a fetch tool with an allowlist. Offline, it shows refusals that need no network; live, it fetches one allowlisted public URL. The README and `scripts/README.md` list it (D9).

#### M11: concurrency foundations

- FR-43: `SchedulerLimits` is a public frozen type with `max_concurrent_tools` (a positive int, default 4, P2-D5), `tool_concurrency_limits` (a mapping from tool name to a positive int, default empty) and `provider_concurrency_limits` (a mapping from model client key to a positive int, default empty); the mappings are copied into immutable mappings at construction. `Runner(scheduler_limits=...)` sets the provider limits, shared by every run that Runner drives, and the default per-run limits; a provider limit naming a key that is not one of the Runner's model clients is refused at `Runner` construction. `RunConfig.scheduler_limits`, when set, replaces the Runner's per-run and per-tool limits as a whole for that run, and a `RunConfig` whose limits carry provider limits is refused at construction, because a limit shared by many runs cannot be set by one of them. Invalid values are refused at construction by field name, as `max_turns` is: a bool, a non-int, less than 1 or more than 2**31-1; a mapping that is not a mapping; and a key that is not an exact, non-empty `str` or that cannot be stored (`unstorable_reason`), so no run completes in memory and fails on Postgres (M5 round 8). Migration `0004` gives `execution_manifests` a `scheduler_limits` JSONB column holding the run's effective limits, NULL for rows written before it, idempotent per FR-17 (P2-D10). The fields the design names for the orchestrator (`max_concurrent_subagents`, `max_tasks_per_run`, `queue_policy`) are added by the second increment, not reserved now.
- FR-44: Parallel tool calls (P2-D2, DECISION-c2da306d, ADR-30, P2-D14). `ToolSpec` gains `concurrency_safe`, a bool defaulting to False that enters `schema_hash` only when True, so every existing tool keeps its hash. The tool calls of one model response are taken in the order the model issued them and split into consecutive batches: a call whose name resolves to a registered tool declaring `concurrency_safe=True` joins the current batch, and any other call, including one naming no registered tool, is a batch of its own. Batches execute one after another. Within a batch, executor steps 1 to 5 (resolve, validate, permission, approval, `before_tool`) run for every call, in issue order, on the event loop's thread, before any call of the batch reaches step 6. A call then acquires its slots immediately before step 6 and releases them after step 9, with at most `max_concurrent_tools` calls of the run, and at most a tool's entry in `tool_concurrency_limits` calls of that tool, between steps 6 and 9 at once. A call's timeout, and the point after which an error carries its declared provenance (FR-40), begin at step 6; a call finishes when its step 9 is done. Each call still yields its own outcome through the executor's total boundary, so one call failing neither cancels nor changes another; if a `BaseException` escapes a call, or the task running the batch is cancelled, the batch's other calls are cancelled and awaited, never left running. Results are appended to history in one tool message in issue order, whatever order the calls finish in. `max_concurrent_tools=1`, or tools that do not declare `concurrency_safe`, reproduce today's strictly sequential execution. Hooks and permission checkers are still called on the event loop's thread, never from two threads, but a call's `after_tool` may now run while another call of its batch is between steps 6 and 9. A synchronous tool implementation still runs inline on the event loop (FR-5) and gains nothing from a batch; the built-in tools are asynchronous. Every `ToolCalled` event now populates the envelope's `tool_call_id`, NULL since Phase 0, so a consumer can pair events with calls without reading payloads.
- FR-45: The built-in file tools (FR-36) run their blocking work (the read, list, glob and grep functions) on a thread pool the SDK owns, never on the event loop's default executor, which every store call uses (FR-20). One pool serves every file tool in the process. It holds 4 threads by default (P2-D6), set with `agentsdk.builtin_tools.set_file_tool_threads(n)` before the first file tool call and refused with `RuntimeError` after it, and its threads are named `agentsdk-file-tool-<n>`. The wait for a pool thread counts against the call's executor timeout; if the timeout expires first, the blocking work never starts. A call already running cannot be interrupted and ends at its own walk budget. With every pool thread busy, store calls are unaffected. Round 1 of the M10 review measured store latency of 139 s with 20 concurrent greps sharing the default pool (KNOWLEDGE-0d5f3a4e, DECISION-ae7e223f). The fetch tool's name resolution still uses the default executor (see Risks).
- FR-46: `provider_concurrency_limits` caps the `ModelClient.send` calls in flight for one model client key across every run of one Runner. A call over the limit waits for a slot and is not refused, and its wait is not part of the client's own timeout. The limit counts `send` calls, not HTTP requests: a slot is held through the client's own retries and backoff (FR-15).
- FR-47: The carry-overs from round 5 of the M10 review are closed. (1) A result whose `source_uri_or_hash` is a `str` subclass is stored with that text copied into an exact `str` with `str`'s own methods, as step 8 copies content, and the 8,192-character bound is measured on the copy, so a subclass reporting a false length is bounded by what it holds (KNOWLEDGE-739aca22). (2) The source bound is pinned: 8,192 characters are accepted and 8,193 refused (KNOWLEDGE-57234fb3). (3) A file or folder name the store cannot hold, such as one with a lone surrogate, no longer turns a whole `list_directory`, `glob` or `grep` result into a tool error at the executor's storability check (step 7): the file tools withhold that entry, and for a folder its whole subtree, count it among the withheld entries, and return the rest.

#### M12: run handles, runtime event streaming and cancellation

- FR-48: `Runner.start(spec, task, config)` is a coroutine that validates configuration exactly as `Runner.run` does, raising the same configuration errors at the call site before any run is started, and then returns a `RunHandle` for a run already under way, without waiting for it to finish. `Runner.run` keeps its signature and its result: it is a run started this way and awaited to its end. A run belongs to the event loop that started it.
- FR-49: A `RunHandle` exposes `run_id`, available at once; `events()`, an async iterator over the run's `RunEvent`s in `sequence_no` order; `result()`, a coroutine returning the run's `RunResult`; `state()`, a snapshot of whether the run is still running or its terminal status, with the usage, cost (None while a model call is in flight) and turns recorded so far; and `cancel(reason=None)`. Every `events()` iterator yields the whole stream from the run's first event, whenever it was opened, then each new event as it is recorded, in `sequence_no` order, holding an event back until every lower number has been yielded; it ends when the run ends, after its terminal event, or after the last recorded event if the terminal event could not be recorded. Several iterators may be open at once, and each receives every event. The events yielded are exactly those in `RunResult.events`, on the in-memory and the Postgres backends alike. `result()` returns the same `RunResult` however often it is awaited. Cancelling a coroutine that awaits `result()` or iterates `events()` does not cancel the run.
- FR-50: Cancellation (P2-D3, DECISION-a44db7e4). `cancel(reason=None)` is idempotent, and has no effect on a run that has already ended or whose terminal event is being written. Once it takes effect, the run starts no further model call and no further tool call; a model call in flight (P2-D7) is abandoned; a model call waiting for a provider slot (FR-46) is abandoned without `send` being called; and tool calls between steps 6 and 9 are cancelled, their implementations receiving `asyncio.CancelledError` when awaitable. A file tool's worker thread already running is not waited for, and its result is discarded (FR-45). A store write or event emission already started when cancellation takes effect is completed, shielded from the cancellation, before the run's terminal writes, and nothing is written for the run after its terminal event. The run then ends with the new terminal status `RunStatus.CANCELLED`: `RunCancelled`, carrying the reason, is emitted once and is the run's last event; `runs.status` is `cancelled`, with usage and cost recorded as on every other terminal path (FR-31); `RunResult.output` is None; and `RunResult.error` carries the reason, or `cancelled` when none was given or the reason cannot be stored. Every tool call of a response whose calls the run had begun to execute is paired with a result: a call that did not finish gets an error result of type `ToolCancelled`, a new `ToolError`, carrying its tool's declared provenance if it had reached step 6 (FR-40, DECISION-ea6e1daf), and its `ToolCalled` event, with `is_error` true, is emitted before `RunCancelled`. A response stopped by `max_tokens` or `content_filter` still keeps its unexecuted calls without results (FR-26, AC-20). Usage is the sum of the calls the model answered. When a model call was in flight at cancellation, `cost_usd` is None (P2-D7, NFR-11). Cancelling the task that awaits `Runner.run`, or a `CancelledError` raised by a collaborator, ends the run the same way, records it, and still raises `CancelledError` to the caller. This amends INVARIANT-af776957 (a cancellation is recorded, then re-raised) and closes KNOWLEDGE-b3c2b462, which had placed the fix in Phase 6.
- FR-51: Migration `0005` makes `runs.status` admit `cancelled`: it drops the check constraint on `runs.status`, found by its definition rather than an assumed name, and adds one admitting `cancelled` beside the existing statuses (P2-D10). `run_events.event_type` has no constraint, so `RunCancelled` needs no migration. The migration is idempotent, per FR-17, and `schema.sql` is not edited.
- FR-52: `EventType` gains `RunCancelled`, and the error taxonomy gains `ToolCancelled(ToolError)`. Every event sink numbers and records events under a lock: `InMemoryEventSink` no longer reads its length and appends in two steps, and the Postgres sink's `events()`, and so `RunResult.events`, are in `sequence_no` order. The `ToolCalled` events of a parallel batch are emitted as each call finishes (P2-D9).

#### M13: artifacts

- FR-53: `ArtifactRef` is a public frozen type with `artifact_id` (a canonical UUID the store issues), `tenant_id`, `project_id`, `uri`, `mime_type`, `content_hash` (the SHA-256 of the content, as lowercase hex), `size` in bytes, `created_by_agent`, `source_run` (a canonical UUID or None), `source_task` (None until plan nodes exist), `provenance`, `classification` (optional text), `created_at` and `expires_at` (timezone-aware, or None). `provenance` is a `ContentProvenance` passed through `primitives.checked_provenance`, the check executor step 8 applies, moved from the executor so the executor and the stores share it: labels must be the enums' own members and the source bounded text. `uri` is `urn:agentsdk:artifact:<artifact_id>`, and names neither a host path nor a credential.
- FR-54: `ArtifactStore` is a protocol whose methods are coroutines: `put`, `get`, `metadata`, `delete` and `expire`, on a store bound to one tenant and project (ADR-11). `Persistence.artifact_store(tenant_id, project_id)` returns the Postgres store for that scope and refuses an empty or unstorable scope. `put` takes the content as `bytes` (a `bytearray`, `memoryview` or subclass is copied into exact `bytes`), a MIME type of the form `type/subtype`, provenance, the creating agent, and an optional source run, classification and expiry time. `mime_type`, `created_by_agent` and `classification` are at most 255 characters and must be storable (`column_rejection_reason(..., "TEXT")`); an expiry time must be timezone-aware and later than the store's clock; and content over the size cap (10,485,760 bytes by default, P2-D8, set per store, with a bool, a non-int or a value below 1 refused) is refused before anything is written. Each refusal of `put` is a `ValueError` naming the field. `put` issues a new `artifact_id`, never deduplicates identical content, and returns the `ArtifactRef`. `get(artifact_id)` takes an id, not a uri, and returns the content after verifying it against `content_hash`, raising `ArtifactIntegrityError` rather than returning content that does not match. `get`, `metadata` and `delete` raise `ArtifactNotFound`, whose message names only the requested id, for an artifact of another tenant or project, a deleted one, an expired one and an id that never existed, indistinguishably. Expiry is compared with the store's clock (`datetime.now(timezone.utc)` by default, injectable): an artifact whose `expires_at` is at or before it is not found by any method even before `expire` runs, and `expire` removes every such artifact of the scope and returns how many it removed. `delete` and `expire` remove rows; there is no update. `ArtifactNotFound` and `ArtifactIntegrityError` are `AgentSDKError`s.
- FR-55: The SDK ships an in-memory `ArtifactStore` and the Postgres one, backed by migration `0006`: an `artifacts` table holding metadata and content, with `tenant_id` and `project_id` NOT NULL and an index leading with `(tenant_id, project_id)` (NFR-2), and `source_run` referencing `runs` (P2-D8, P2-D10). Both implementations behave identically under FR-54. A `source_run` must be a run of the same tenant and project, as a parent run must be (FR-21): the Postgres store checks it in the same statement as the insert, as `start_run` checks `parent_run_id`, and the in-memory store is built with a callable `(tenant_id, project_id, run_id) -> bool` naming the runs it may accept, and refuses every `source_run` without one. The Postgres store does its I/O through `asyncio.to_thread` and reaches the database only through the connection pool, so no artifact I/O runs on the event loop's thread (FR-20). Test cleanup removes artifacts before the runs they name.
- FR-56: `scripts/11_run_handle.py` streams one run's events through a `RunHandle` and cancels a second run mid-flight, and `scripts/12_artifacts.py` puts, reads and scopes an artifact (P2-D11). Both run in both FR-24 modes, the README and `scripts/README.md` list them, and `tests/test_distribution.py`'s `EXPECTED_EXAMPLES` gains 09 to 12; 13 is added with its example in M14 (FR-60; owner decision, 2026-09-15).

#### M14: timings and a minimal OpenTelemetry exporter

- FR-57: Every `ModelCalled` payload records `started_at` (UTC, ISO-8601, the wall-clock time `ModelClient.send` was entered), `duration_ms` (a float, measured with `time.perf_counter_ns` around `send`), `queued_ms` (the wait for a provider slot before `send`, FR-46), `model`, the model the request was sent with (a `before_model` hook may change it; with no model named it is FR-32's recorded model; FR-30 prices by it), `provider`, the model client key, fixed for the run, and `provider_name`, the name the client declares through an optional read-only `provider_name` attribute, read once per run as FR-32 reads `default_model_id`, or None when it declares none (`ModelClient` stays `send()`-only). `RunStarted` records the run's `parent_run_id` (FR-21), None for a top-level run, so a run's own events name its parent. Every `ToolCalled` payload records `started_at` (at step 6), `duration_ms` from step 6 to step 9, and `queued_ms`, the wait between the executor receiving the call and its slots being granted (FR-44), so a slow tool and a saturated limit can be told apart; a call that never reached step 6 records `started_at` as None and both measures as 0. The terminal event records the run's `started_at` and `duration_ms`. A model call that raises `ModelError` emits no `ModelCalled` and so records no timing. Payloads are JSONB, so no migration is needed, and a timing never changes a run's outcome.
- FR-58: `agentsdk.telemetry`, a single module not imported by `import agentsdk`, provides `OpenTelemetryExporter`, built with a `TracerProvider` the caller owns. It turns a run's events into spans after they happen, from the recorded timings: the run becomes an `invoke_agent` span, each `ModelCalled` a `chat` span and each `ToolCalled` an `execute_tool` span beneath it. A run whose parent run's `invoke_agent` span this exporter instance has already started is linked to that span; any other child run carries `agentsdk.parent_run_id` only. The parent is read from the run's own `RunStarted` event (FR-57). It consumes a `RunHandle` (FR-49) or a finished `RunResult`, so it adds nothing to the path a run takes.
- FR-59: Span attributes follow OpenTelemetry semantic conventions v1.40.0 (P2-D12), and every span records that version as `agentsdk.semconv_version`: `gen_ai.operation.name`; `gen_ai.agent.id`, the `AgentSpec.id`; `gen_ai.request.model`; `gen_ai.provider.name` only when the model client declares a provider name, read from `ModelCalled.provider_name` (FR-57), with the client key as `agentsdk.model_client_key`; the token counts M9 records, as `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.usage.cache_read.input_tokens` and `gen_ai.usage.cache_creation.input_tokens`; `gen_ai.response.finish_reasons`; and on a tool span `gen_ai.tool.name`, `gen_ai.tool.call.id`, `error.type` when the call failed, `agentsdk.tool.is_error` and `agentsdk.tool.truncated`. Every span carries `agentsdk.run_id`, `agentsdk.tenant_id` and `agentsdk.project_id`, and `agentsdk.parent_run_id` when set. A call's cost is exported as `agentsdk.cost_usd`, a decimal string, only when it is known: an unknown cost is absent, never 0 (NFR-11). No message content, tool argument or tool result is exported, and no credential.
- FR-60: Telemetry never affects a run. The exporter owns one worker thread fed by a bounded queue, and every span is created and ended on that thread, whatever span processor the caller's provider uses, so a synchronous processor or a blocking exporter cannot stall the event loop. A full queue drops events and increments `OpenTelemetryExporter.dropped`; an exception increments `OpenTelemetryExporter.errors`; neither is raised. An exporter, tracer provider or collector that raises, stalls or cannot be reached changes no run's status, result, events or stored rows. `scripts/13_telemetry.py` shows a run's span tree through an in-memory exporter offline and sends it over OTLP/HTTP to `OTEL_EXPORTER_OTLP_ENDPOINT` live (P2-D11); `.env.example` names that variable and AC-17's offline run removes it, and `tests/test_distribution.py`'s `EXPECTED_EXAMPLES` gains 13 (owner decision, 2026-09-15; see FR-56). The README shows the SQL-dashboard route over Postgres, which needs no exporter.

#### M16: the plan as a persisted object

- FR-64: `PlanNode` is a public frozen type with `node_id` (an exact non-empty `str`, unique within its plan), `objective`, `dependencies` (node ids in the same plan), `assigned_role`, `input_refs`, `expected_output_schema` (a JSON Schema document or None), `acceptance_criteria` (FR-74), `budget_reservation` (FR-67) and `side_effecting`, a bool defaulting to True (P2-D18), with optional `timeout`, `retry_policy` and `risk_class`. Every field is validated at construction by field name, as `SchedulerLimits` is (FR-43): a value the store cannot hold is refused there (`unstorable_reason`), so no plan completes in memory and fails on Postgres. A plan whose dependencies name an unknown node, or form a cycle, is refused: ADR-02 is DAG-only, and P2-D17 adds no loop node.
- FR-65: `PlanVersion` is immutable and carries `plan_id`, `version`, `parent_plan` (the `plan_id` and `version` it was replanned from, or None for the first), `run_id`, `nodes`, `created_at` and `plan_hash`, the hash of its canonical JSON. A planner's output is a JSON document validated against a schema shipped with the package; a document that fails validation is refused with the failing path, and no partial plan is stored. Storing a plan never mutates an earlier version: a replan writes a new version whose `parent_plan` points at the old one, so the chain of what was tried is readable after the run. Migration `0007` adds `plan_versions` and `plan_node_states`, both carrying non-null indexed `tenant_id` and `project_id` (NFR-2), idempotent per FR-17.
- FR-66: `RunStateStore` records each node's status for a run: `pending`, `ready`, `running`, `done`, `failed`, `skipped`, and `cancelled`. Transitions are recorded through the same event stream as everything else, so a consumer following `RunHandle.events()` (FR-49) sees `PlanNodeStarted` and `PlanNodeFinished` envelopes carrying `node_id`, `plan_id` and `version`, with `sequence_no` unique and contiguous (NFR-17). Both stores implement it, and a node's status is read back exactly as written. `scripts/14_plan.py` builds a two-node plan, stores it, replans it once and prints both versions with their parent link.

#### M17: the budget governor

- FR-67: `BudgetPolicy` is a public frozen type with `run_ceiling_usd`, `run_ceiling_tokens` (at least one set; both may be), `orchestrator_reserve_fraction` (default 0.20), `unallocated_reserve_fraction` (default 0.20), `reservation_cap_fraction` (default 0.40) and `max_replans` (FR-75), each validated at construction by field name (P2-D19). A run's ceiling is split at plan time: the orchestrator reserve, the unallocated reserve, and a reservation for each node. The planner proposes each node's `budget_reservation`; a proposal above `reservation_cap_fraction` of the currently unallocated pool is capped to it, and nodes that propose none split what is left equally. Additional allocation comes only from the unallocated reserve, by deterministic orchestrator policy, never at a model's request (ADR-06, DECISION-e1bf0327).
- FR-68: Enforcement is soft and checked before each model call. An agent at or over its reservation makes no further call, so it can exceed that reservation by at most one call, and a run's committed plus spent budget can exceed its ceiling by at most one call per concurrently running agent, the orchestrator included; `max_concurrent_subagents` (FR-72) bounds that overshoot to 4 by default. Overshoot is charged to the run. A child that reaches its reservation, and a run that reaches its ceiling, end `failed` with reason `budget_exceeded`; once a run's spend reaches its ceiling no new model call and no new child run starts. Unspent reservation returns to the run pool when a node ends, in whichever units have a ceiling. A nested child reserves from its parent's reservation, never from the run pool; retries of a node draw on that node's reservation; replanning stays inside the run ceiling. Migration `0008` records the run's effective `BudgetPolicy`, its reservations and its final spend in the `execution_manifests` row, NULL for rows written before it, idempotent per FR-17. Budgets for plain single-agent runs stay out of scope (backlog I-04).
- FR-69: A dated price table ships inside the package and is the default source of `ModelPricing` (P2-D20). It names its own date, which is reported wherever a price is used and recorded in the `ExecutionManifest`, so a stale price is never read as current fact. A caller-supplied `ModelPricing` overrides it for that model. A USD ceiling on a model the effective pricing does not cover is a configuration error raised at the call site, naming the model, not a silently unpriced run; a token ceiling always applies, priced or not, and an unknown cost stays None and is never reported as 0 (NFR-11). `scripts/15_budget.py` runs a plan whose second node exceeds its reservation and prints the reservations, the reclaim and the `budget_exceeded` ending.

#### M18: subagents

- FR-70: The orchestrator spawns a subagent as its own run, linked by the existing `runs.parent_run_id` (migration `0002`) and `RunStarted.parent_run_id` (FR-57), inheriting the parent's `tenant_id`, `project_id` and `PrincipalContext`. Topology is hub-and-spoke: a child is briefed only by its parent and returns only to its parent, and children never address one another. The briefing is curated, not inherited wholesale: a child receives its node's objective, its `input_refs` resolved through the run's artifact store, and nothing else of the parent's history. Every result a child returns carries the provenance and taint of its inputs, at the maximum taint of them (Phase 0's propagation rule), so a tainted child result cannot launder itself by crossing a run boundary.
- FR-71: A node with an `expected_output_schema` populates `ModelRequest.output_schema` for its child, the first use of that field. A result that does not validate is re-asked once, with the validation error appended to the child's history, and if the second result also fails the node ends `failed` with reason `output_contract_violation` (P2-D22). Both attempts draw on that node's reservation, so a model that cannot produce the schema cannot escape the budget by failing repeatedly. The invalid text is kept in the child's history and in its stored messages, so the failure is inspectable rather than merely reported.
- FR-72: `SchedulerLimits` gains `max_concurrent_subagents` (default 4), `max_tasks_per_run` (default 50) and `queue_policy` (`fifo`, the only value this increment accepts), added now rather than reserved in M11 (FR-43), and validated the same way. Recursion is bounded at depth 3 (P2-D21): the orchestrator is depth 0, and a spawn at depth 3 is refused with `MaxDepthExceeded`, a new error in the taxonomy, which fails that node without cancelling its siblings. A run that would exceed `max_tasks_per_run` refuses the spawn the same way. `scripts/16_subagents.py` fans out three children under a limit of 2 and prints their parent link, the peak concurrency and one refused spawn at depth 3.

#### M18a: validation, the loop-thread guard, and briefed-input provenance

Four caveats from M18's round 4 review, specified before M19 so the guard exists before the
orchestrator adds store call sites of its own (owner decision 2026-10-07).

- FR-79: `RunConfig` refuses an invalid `depth` or `output_schema` at construction, by field name, as `max_turns` does (FR-43): `depth` must be an `int` of 1 or more and at most 2**31-1, and a `bool` is refused; `output_schema`, when not None, must be a mapping. Round 4 caveat C1: today both are accepted, and a non-mapping schema surfaces only later as "the schema could not be applied", a re-ask and a failed run.
- FR-80: `Briefing` validates `expected_output_schema` at construction -- None or a mapping -- and refuses anything else by field name. A refused briefing never reaches `SubagentPool.spawn`, so it cannot consume a task count in `_admit`, write a row, or change what `spawned()` reports. Round 4 caveat C2: `"abc"` raises a bare `ValueError` from `spawn` after admission.
- FR-81: The property DECISION-6b62d1f5 states -- every store call made during a run goes to a worker thread -- is asserted of every store call, not of a list of paths. An autouse fixture wraps `postgres._pool` for every test in the suite and fails any connection checkout made from a thread that has a running event loop, naming the store method and the test. `test_no_store_call_runs_on_the_event_loop_thread_on_any_run_path` remains as a second check, and its docstring records that the fixture is the guarantee. Round 4 caveat C4: forcing the artifact read in `_brief` onto the loop passes that test, because its sixth path spawns with no artifact store, and the cancelled-child path is in no guard at all.
- FR-82: Every Postgres store reaches the database through one checkout helper, which refuses when `asyncio.get_running_loop()` succeeds in the calling thread, so a new call site cannot violate FR-20 even where no test covers it. The refusal is on by default under tests, where a violation must fail loudly, and off by default in production, where it logs once and proceeds, so a latent violation costs latency rather than a run.
- FR-83: `ContextAssembler`'s provenance manifest gains an entry for every briefed input a subagent receives: the input's uri or hash, origin, instruction authority, trust zone and taint flags, carried as request metadata beside the tool-result entries it already lists (ADR-26), never as text the model reads. A child briefed with no inputs adds no entry. Round 4 caveat C3, owner decision 2026-10-07.
- FR-84: The briefing marks a briefed input as data: each input block is delimited and labelled data rather than instructions, naming its uri or hash. The marker is signalling only -- ADR-17 stands, and the enforceable half is FR-83's manifest entry and the policy that reads it -- and `scripts/16_subagents.py`'s check that a child ignored an injected instruction asserts the result's provenance instead of a substring of the child's text, which passes whenever the model paraphrases.

#### M19: the orchestrator

- FR-73: `Orchestrator` executes a `PlanVersion` over its DAG: a node becomes `ready` when every dependency is `done`, ready nodes run concurrently within `max_concurrent_subagents`, and queueing is FIFO. Cancellation reaches children: cancelling the run cancels every running child and awaits it, and no child is left running once the parent has returned or raised (NFR-17, FR-51). A node that fails does not cancel its siblings; nodes that depend on it become `skipped` unless replanning (FR-75) supersedes them. The orchestrator itself is an agent run with its own reservation, so its planning calls are counted, not free.
- FR-74: A node is `done` only when its execution terminated successfully, its output validated against `expected_output_schema` when one is set, and every acceptance criterion is satisfied (P2-D16). This increment evaluates three deterministic kinds: `output_schema`, already covered by FR-71; `artifact_exists`, naming an artifact whose `content_hash` must match what the node recorded (M13); and `tool_succeeds`, naming a registered tool and arguments that must return a non-error outcome, executed through the normal executor with the node's permissions. A `critic` criterion parses and stores, so a plan written now stays valid when Phase 3 builds the critic, but a run that reaches one ends that node `failed` with reason `criterion_not_available`, naming it. A criterion that is not satisfied fails the node with `acceptance_criterion_failed`, naming which.
- FR-75: Replanning is automatic while the run's budget remains, the replan count is below `max_replans`, and the failure is replannable (P2-D18). It produces a new `PlanVersion` whose `parent_plan` is the version that failed, inside the same run and the same ceiling. A node already `done` and `side_effecting=True` is carried into the new version as `done` and is never rerun; a `done` node with `side_effecting=False` may be rerun. When the budget is spent, or `max_replans` is reached, the run ends `failed` carrying the last plan version, not a silent success. `scripts/17_orchestrator.py` runs a four-node plan in which one node fails its acceptance criterion, prints the replan and shows that the completed side-effecting node was not rerun.
- FR-76: A tool reaches its run through an explicit `RunScope` argument (P2-D26), carrying `run_id`, `tenant_id`, `project_id`, the node id when one applies, and the artifact store bound to that run. A tool that declares no `RunScope` parameter is called exactly as before, so every existing tool and every built-in keeps working unchanged and no `schema_hash` moves. A tool that declares one receives it, and the artifact it writes through that scope is attributed to the run and node that wrote it.

#### M20: context policy and compaction

- FR-77: `ContextPolicy` decides what an agent sees, and tool visibility follows execution (P2-D23): an agent is sent only the schemas of the tools its `tool_profile` permits it to execute, reversing DECISION-ca1ad3e0 for orchestrated runs. A call to a tool the agent cannot see is refused exactly as an unknown tool is today. Because two runs with the same manifest must have seen the same tools, the `ExecutionManifest` records the qualified names and `schema_hash` values actually sent, and migration `0009` adds that column, NULL for rows written before it, idempotent per FR-17. The policy is also the single place that decides what of a parent's history a child sees (FR-70), so briefing rules are readable in one type rather than spread through the orchestrator.
- FR-78: `ContextCompactor` compacts an agent's history when the assembled prompt passes a configurable fraction of the model's context window, default 0.75 (P2-D24), a separate type from `ContextAssembler` (Phase 0) and `ContextPolicy`. The summary it produces inherits the maximum taint of everything it summarises and keeps the provenance of every source it names, so compaction never launders a tainted input into an untainted summary. Every compaction is recorded as an artifact holding what was replaced and as a `ContextCompacted` run event naming that artifact, the token counts before and after, and the model call that produced the summary, which is charged to the agent's own reservation. A run that has been compacted therefore remains auditable end to end. `scripts/18_context.py` runs a long agent past the threshold and prints the visible tool set, the compaction event and the artifact it wrote.

## Non-functional requirements

- NFR-1: Provider-agnostic. Switching between `openai.*`, `bedrock.*`, `azure.*`, and `vertex_ai.*` models is a configuration change only — no SDK source file changes, no new adapter.
- NFR-2: Multi-tenant by construction. Every row in every table carries non-null, indexed `tenant_id` and `project_id`.
- NFR-3: Auditable. Any completed run reconstructs from `runs` + `messages` + `run_events` together. Events alone are explicitly not the source of truth.
- NFR-4: No credential ever reaches model context, a persisted row, or a `RunEvent` payload.
- NFR-5: The public API surface is `AgentSpec`, `RunConfig`, `Runner`, `RunResult` only. No internal collaborator is imported by application code or by the golden eval.
- NFR-6: No runtime dependency on LangGraph, Claude Agent SDK, or OpenAI Agents SDK. The SDK must import and run with none of them installed.
- NFR-7: Phase 0 interfaces are chosen so Phases 2–6 add fields and implementations rather than replace contracts.
- NFR-8: Persistence is not the concurrency ceiling. With several runs executing concurrently against a model client that performs no network I/O, the worst single event-loop stall stays under 50 ms, and wall-clock time stays within 3x the same workload run entirely in memory. Measured today: 1008 ms worst stall and roughly 30x wall time.
- NFR-9: Example-only dependencies (the MCP client library) live in `scripts/requirements.txt` and the package's `examples` extra, never in the SDK's runtime dependencies, so NFR-6's guarantee that the SDK imports with nothing extra installed is unchanged.
- NFR-10: The repository carries a README describing what Phase 0 and M7 actually do and what they do not -- no streaming, subagent orchestration, native MCP, sandboxing, human approvals, context compaction, budgets or resume -- an MIT `LICENSE`, and a `.env.example` naming every variable the SDK and examples read, with no values.
- NFR-11: Accounting never fails a run and never guesses. Token and cost computation cannot raise on any value `Usage` or `ModelPricing` can hold. `cost_usd` is either None or a finite, non-negative `Decimal`, including when counts are inconsistent (cache tokens exceeding prompt tokens) or negative.
- NFR-12: A run that sets none of M9's options sends the same request payload it sent before M9. The existing tests pass unchanged, and any edit a test needs is listed and justified in the review prompt.
- NFR-13: The built-in tools add no runtime dependency beyond `httpx` and the standard library (NFR-6, NFR-9).
- NFR-14: No input a model can send to a built-in tool raises past the executor or blocks the event loop, and no refusal message discloses content or a resolved path outside the tool's confinement.

- NFR-15: Phase 2's first increment keeps existing behaviour. A turn with at most one tool call, and any run with `max_concurrent_tools=1`, sends the same request payloads and produces the same history and events as before Phase 2, apart from the envelope `tool_call_id` FR-44 populates on `ToolCalled` events, the payload fields FR-57 adds, the carry-overs FR-47 closes, and one ordering FR-44 requires: under `max_concurrent_tools=1` a batch of `concurrency_safe` calls still passes every call through steps 1 to 5 before the first executes, so `before_tool` sees every call of the batch first, and a call refused at those steps records its `ToolCalled` before the events of calls issued ahead of it, while history and the results the model receives keep issue order (owner decision, 2026-09-14, M11 review A1). A run whose tools do not declare `concurrency_safe` is likewise unchanged. The existing tests pass unchanged, and any edit a test needs is listed and justified in the review prompt; the increment already expects edits to `tests/test_golden_eval.py` (cleanup, NFR-16) and to `tests/test_distribution.py` (`EXPECTED_EXAMPLES`, and `CONFIG_VARS` for FR-60).
- NFR-16: The regression suite leaves the store as it found it. A full run adds no row to `runs`, `messages`, `run_events`, `execution_manifests` or `artifacts`; before Phase 2 the golden-eval tests left 13 runs behind on every full run.
- NFR-17: Concurrency and cancellation never corrupt the record. Under parallel tool calls, provider limits and cancellation, every run's `sequence_no` values stay unique and contiguous on both stores, no run is left `running` once `Runner.run` or `RunHandle.result()` has returned or raised `CancelledError`, provided the store accepts the terminal write, and a run's usage equals the sum of its `ModelCalled` events.
- NFR-18: Phase 2's first increment adds no runtime dependency (NFR-6, NFR-13).
- NFR-19: Telemetry is optional: `import agentsdk` does not import OpenTelemetry, and the exporter works only when `opentelemetry.sdk` is importable, naming the `otel` extra when it is not (NFR-6, NFR-18).
- NFR-20: The comparison is never an SDK dependency: `claude-agent-sdk` appears only in the `eval` extra and in `evals/adr12/requirements.txt`, no module under `agentsdk/` imports it, and nothing the harness writes contains a credential (AC-19).
- NFR-21: Phase 2's second increment adds no runtime dependency (NFR-6, NFR-13, NFR-18). The plan schema, the price table and the compaction summary all use what the SDK already carries.
- NFR-22: Orchestration never corrupts the record. Under parallel subagents, replanning and cancellation, every run's `sequence_no` values stay unique and contiguous on both stores, no child is left `running` once its parent has returned or raised, every child's `parent_run_id` resolves to a run that exists, and a plan version is never mutated after it is stored (NFR-17).
- NFR-23: Budgets and prices are honest. A run's recorded spend equals the sum of its `ModelCalled` costs plus its children's, an unknown cost stays None rather than 0 (NFR-11), the shipped price table reports its own date wherever it is used, and the overshoot soft enforcement permits is bounded by `max_concurrent_subagents` and charged to the run rather than hidden.

## Constraints

- Python with async/await, matching the existing FastAPI/LangGraph stack.
- PostgreSQL is the sole durable backend; one database, multiple tables, no separate infrastructure per store.
- The model endpoint is the configured `BASE_URL` LiteLLM gateway, authenticated by `MODEL_API_KEY` from `.env`. Both are read from environment, never committed.
- The gateway blocks `GET /v1/models` at the Envoy layer (403 "fault filter abort"); the working model-listing path is `GET /models`. `POST /v1/chat/completions` works normally.
- Windows development host: PostgreSQL 16 native service on localhost:5432, Docker daemon currently not running.
- Personal product development (ADR-04) — no external review gating.
- M10's AC-28 creates real symlinks, which this host refuses without Windows Developer Mode (measured 2026-09-12: WinError 1314 for file and directory symlinks; junctions, hard links and alternate data streams succeed). Developer Mode must be on before M10's gate is run (D7).

## Non-goals

- No subagents, orchestrator, DAG, plan versioning, budget enforcement, `ContextPolicy` or replanning yet: they are Phase 2's second increment (DECISION-ce3b0e78).
- Phase 2's first increment streams a run's events only within the process running it; there is no cross-process subscription to another process's runs.
- Cancellation cannot interrupt a worker thread already running a file tool; that thread ends at its own walk budget (FR-45).
- Tools receive no run context in the first increment, so a tool cannot yet write an artifact on its own run's behalf; the second increment decides how a tool reaches its run.
- No evidence ledger, claims, or critic (Phase 3).
- No MCP, tool catalog, credential brokering, or approval manager (Phase 4).
- No sandbox or workspace (Phase 5).
- No durable interruptions, replay, or idempotency (Phase 6).
- No context compaction in the first increment. The owner moved it from Phase 7 to Phase 2's second increment on 2026-09-14.
- M14 exports a minimal span tree and no content; the full OpenTelemetry mapping and compatibility enforcement stay in Phase 8.
- M15 measures; it builds no general-agent capability. A general-agent preset and a model-driven autonomous mode alongside the DAG are Phase 5A (owner, 2026-09-14).
- No streaming of model tokens. `RunHandle` (M12) streams runtime events, not tokens.
- No structured-output enforcement beyond the unused schema slot.
- None of the three Stage 2 products is built or started.
- M8 adds no SDK capability. Examples that reach toward later phases (MCP, delegation) bridge or record by hand and say that they do.
- M9 measures and records cost; it enforces no budget. ADR-06's ceilings and reservations are Phase 2.
- M9 changes only the `max_tokens` and `content_filter` stop reasons. An unrecognised stop reason still ends the run as it does today.
- M9 sends no prompt-cache markers and returns no thinking blocks (Phase 0/1 native Anthropic adapter).
- M10 adds no write or edit tools (Phase 4), no shell or code execution (Phase 5), and no bundled search provider.
- M10 adds no visibility filtering. Under DECISION-ca1ad3e0, registered built-in tools are offered to every agent even when they are not in its profile; the profile gates execution only. Recorded, unchanged.

## Risks

- **A published history publishes every file ever committed.** Removing a file from the tree does not remove it from history, so an exclusion applied only to the current tree publishes the excluded file anyway. Mitigation: decide what is published per commit, not per tree, before the first push.
- **Examples drift from the SDK.** An example that stops running teaches a wrong API with the authority of the repository behind it. Mitigation: AC-17 runs every example in the gate.
- **Provider neutrality is only half-proven.** AC-9 switches upstream providers, but through one gateway speaking one wire format. That proves model-agnosticism, not wire-format-agnosticism; a genuinely second wire format remains unproven until a non-LiteLLM adapter exists. Mitigation: state the limit honestly now, keep `ModelClient` the only place provider shape is known, and treat the second wire format as Phase 0/1's real exit criterion rather than pretending Phase 0 closed it.
- **Postgres credentials.** Resolved: the harness connects to `<db_name>` as `<db_user>` (ASSUMPTION-6c8f0f59), and every database-backed gate since M5 has run against it. An M10 verification probe printed the password on 2026-09-13. The owner declined rotation for now, because this database is for development only (DECISION-1a5942ea); revisit if it becomes reachable from other machines, the password is used anywhere else, or it moves toward shared or production use. Probes must never print a password or a connection string.
- **Gateway reachability is partly filtered.** `GET /v1/*` is blocked by Envoy today. If the filter later extends to POST paths, every model-backed gate fails for reasons unrelated to the code. Mitigation: keep a scripted stub `ModelClient` so loop logic stays testable without the network.
- **Unused seams may be designed wrong.** `RunInterruption`, `ToolExecutionOutcome`'s unreachable variants, and `PrincipalContext` are specified against needs no Phase 0 code exercises. Mitigation: accepted deliberately and bounded — each is a type or a column, not a subsystem.
- **A connection pool is a new runtime dependency.** FR-20 most likely needs `psycopg_pool` (via `psycopg[binary,pool]`) and touches every store method. Mitigation: NFR-6 forbids vendor agent SDKs, not infrastructure libraries, and `psycopg_pool` is maintained by the psycopg project itself — but the choice is a decision to record, not a detail to slip in.
- **Hardening an approved milestone can regress it.** FR-17 through FR-21 change `postgres.py`, which M5 took nine review rounds to approve. Mitigation: the existing 423 tests are the regression gate and must stay green unchanged; any test that has to be edited to accommodate a change is a signal to re-examine the change, not the test.
- **A single golden eval carrying three assertions may pass for the wrong reason.** Mitigation: assert each path independently rather than asserting only the final status.
- **Cache semantics for Anthropic over the gateway are unverified.** Caching could not be triggered without cache markers, which this adapter cannot send, so FR-29's "prompt includes cache tokens" was measured for OpenAI only. Mitigation: the adapter normalises to the canonical meaning; re-verified when the native Anthropic adapter lands.
- **Reasoning effort changes the conversation shape.** Claude returned `thinking_blocks` and `reasoning_content`, which `Message` cannot carry. A two-turn tool loop without them returned HTTP 200, with 0 reasoning tokens on turn 2 in one observation. Mitigation: recorded, and carried by the Phase 0/1 decision to return thinking blocks.
- **An `after_tool` hook can overwrite declared provenance with a more trusted one.** ADR-26 says only a validator or policy decision may clear taint, and a hook is developer code. Recorded; not closed in M10.
- **Address pinning must keep TLS correct.** Connecting to a checked IP must still verify the certificate against the host name. Mitigation: AC-30 runs its success path over TLS.
- **Parallel tool calls change what a hook observes.** Before Phase 2 a hook saw one tool call at a time; under FR-44 its `before_tool` and `after_tool` for two calls of one turn can interleave, so a hook that keeps per-call state in shared fields can mix them up. Mitigation: FR-44 states the contract, `max_concurrent_tools=1` restores sequential calls, and AC-35 covers mixed batches.
- **Cancellation cannot stop a thread.** A file tool already running continues to its walk budget after `cancel()`, holding a file-tool pool thread. Mitigation: FR-45's bounded pool and queue removal bound the cost; stopping work that is already running belongs to Phase 5's sandbox.
- **A tool that ignores cancellation cannot be stopped.** Cancellation is cooperative: a tool that catches `CancelledError` and carries on delays the end of its run for as long as it runs, and the run ends `cancelled` only when that tool returns or raises. Mitigation: the tools the SDK ships all stop when cancelled; no grace period is added, so no call is ever left running behind a run (FR-44), and stopping arbitrary code belongs to Phase 5's sandbox (owner decision, 2026-09-14, at the M12 pre-flight).
- **A model call in flight at cancellation may be billed and uncounted.** Mitigation: P2-D7 reports the run's cost as unknown rather than understate it; exact counting arrives with the `ModelClient` contract change of DECISION-0e3ed41b.
- **Artifacts in Postgres are read whole into memory.** Mitigation: the per-artifact cap (P2-D8); streaming reads wait for a workload that needs them.
- **The first increment's surfaces are specified before their main consumer.** `RunHandle`, `SchedulerLimits` and `ArtifactStore` exist for an orchestrator not yet specified. Mitigation: minimal surfaces with no reserved fields, and NFR-7's rule that the second increment adds fields and implementations rather than replacing contracts.
- **Provider limits are per Runner, not per process.** Two Runners sharing one gateway each enforce their own limit. Mitigation: stated plainly; a process-wide limiter is a hardening item if a workload needs one.
- **Telemetry can carry tenant data out of the database.** Mitigation: M14 exports no content (FR-59), every span carries its tenant and project so a backend can separate them, and AC-46 walks every attribute for content and credentials.
- **The GenAI conventions are in Development status,** so attribute names can change. Mitigation: one pinned version, recorded on every span (P2-D12).
- **The comparison may not run as designed.** The Claude Agent SDK may not accept the gateway, or the gateway's Claude model ids may not map to its model names. Mitigation: FR-63's pre-flight stops M15 for an owner decision instead of letting a substitute stand in.
- **Twelve tasks cannot prove general capability.** Mitigation: the report states its task set and makes no general claim; the set grows with Phase 5A.
- **Name resolution still shares the default pool.** The fetch tool resolves DNS through `loop.getaddrinfo`, which runs on the executor store calls use, and M11 lets fetch calls run in parallel. Mitigation: bounded by `max_concurrent_tools`; resolution moves to an SDK pool if a workload shows contention.
- **A running walk can delay interpreter exit** by up to its 20-second budget, because pool threads are joined at exit. Mitigation: stated; the walk budget bounds it.
- **Artifact reads carry hex.** psycopg reads `BYTEA` as text by default, so a 10 MiB read carries about 20 MiB. Mitigation: bounded by the cap and the pool size; the store reads `content` in binary where it can.
- **The comparison is not like for like.** The arms use different wire formats, only the Claude arm sends cache markers, and the Claude Agent SDK's own cost is an estimate. Mitigation: one `ModelPricing` for both arms, the estimate labelled separately, and each arm's wire format named in the report.
- **A tracer provider's shutdown can block exit** for up to 30 s behind a blocking exporter. Mitigation: example 13 shuts its provider down with a timeout.
